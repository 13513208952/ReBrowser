# 桌面歌词、三态媒体按钮与系统进度修正

本实现纳入[v1.0.4](releases/v1.0.4.md)。本页保留私有 `1.0.4-dev-lyrics1` 至 `lyrics7` 的分阶段诊断／修正记录，不把候选或本机有限观察当成最终APK的全厂商验收。完整页布局与歌词来源见[前序记录](MUSIC_EXPANDED_PLAYER_AND_LYRICS.md)。

## 机主补充要求

同一个系统媒体歌词按钮依次切换 **关闭 → 解锁可拖动 → 锁定穿透 → 关闭**。手机上下拖动；平板不论横竖均可上下左右拖动。歌词不能拖出屏幕而被裁切，锁定后关闭再开启须记住位置。

机主随后补充：锁定背景应完全透明，悬浮歌词不应显示任何说明性文本；另报告手机系统播放控件拖动进度跳转有问题。教室环境中不调整系统音量，网络较差本身不算程序故障。

## 实现与权限边界

- 全量包的媒体会话加入固定 `cycle-lyrics` 自定义动作；旧通知使用同一含运行时 nonce 的不可变 PendingIntent。停止／旧会话不能由按钮复活；喜欢、评分和原播放动作不变。没有新增快捷设置磁贴或公开控制入口。
- `ReBrowserMusicLyrics` 仅解析固定 provider 的有界结果，按实际观测的毫秒进度选择当前行；不自造播放时钟，不重复扣官方 offset，不把歌词当 HTML。
- `ReBrowserMusicRuntime.readLyrics` 有独立单待执行回调槽；超时不假装取消。服务按文档／曲目代际丢弃旧结果，最多保留一份有界歌词；关闭时不新增读取。屏幕关闭／锁屏时移除窗口，不唤醒屏幕、不覆盖 keyguard，不为歌词增加唤醒锁。
- 仅 `src/full` 声明可选 `SYSTEM_ALERT_WINDOW`。未获准时点击按钮仍为关闭，并提示回音乐界面；原生说明弹窗只有用户点击“前往系统授权”才打开本包的系统权限页。返回后仍须再次点歌词按钮，不自动开启。不做 ADB 静默授权。
- 原生音乐／登录界面继续使用既有隐藏悬浮窗保护；其他应用主动隐藏悬浮窗时也尊重其策略，不绕过保护。

## 拖动、锁定与记忆

只有一个小型 `TYPE_APPLICATION_OVERLAY` 窗口。解锁时接收本窗口内拖动，手机固定横向居中，平板允许两轴；使用既有原生设备分类，不以方向或分屏宽度猜设备类型。

`ReBrowserMusicLyricWindow` 将位置限制在窗口可用区域，并按系统栏／cutout 等安全边界及窗口变化重新校正；内容窗口也有尺寸上限。位置按可移动范围比例保存到私有偏好，保留旋转后的相对位置；同一尺寸下关闭再开恢复原像素位置。只保存位置，不保存歌词正文；新运行时仍默认关闭，播放仍按原规则默认暂停。

锁定同时设置 `FLAG_NOT_TOUCHABLE` 与 `FLAG_NOT_FOCUSABLE`。Android 12 及以上还将**整个窗口 alpha** 限制到系统最大遮挡透明度以内（至多 0.75），避免仅设置穿透标志却被系统拦截下层触摸。这个窗口 alpha 不意味着保留黑色背景：`lyrics2` 的锁定 View 背景色 alpha 为 **0**。

`lyrics2` 移除说明标签，只保留一个歌词 TextView；加载中、无歌词、超时等情况也不在浮层显示说明文字。解锁时保留用于定位拖动的半透明底，锁定时完全去掉底色。当前浮层最多三行，超长内容按边界省略；这与拖出屏幕造成裁切是不同问题。

## 系统进度拖动：仍未定位机主报告的失败

课堂仅进行保持暂停的有限诊断，不主动出声：

1. 原音乐 Profile／恢复资源中通过 Android MediaController 发 `seekTo`，4000→9000ms 后 provider 状态先变，媒体会话在后续轮询跟上；12 个样本保持暂停，随后恢复 4000ms。
2. 对当前 Android 16 系统媒体卡片的**真实进度条手势**，4000→103295ms，卡片显示 01:43、原生会话同步更新，仍暂停。
3. 自目标临时辅助包仅在原生仍暂停且进度未被机主改动时请求恢复 4000ms，并确认成功；辅助包随后禁用。

这些只能说明该次**暂停／恢复资源**路径可用，不证明播放中已加载引擎、音频实际位置、试听、快速连续拖动或弱网下 seek 全部正常。没有据此改 seek 代码、宣称机主问题修好，也不把问题归咎于教室网络；仍待机主说明是播放中不跳转、回弹还是其他表现。

## lyrics3：最初安装与 seek 诊断（历史阶段）

为继续定位而不是猜测修复，开发树增加 DUMP 保护下的有限计数／固定结果名：系统收到次数、原生排队／网页提交／拒绝、当前文档观察到的 SDK 成功／失败回调计数。只接收固定白名单结果并将计数饱和在 1,000,000；不保存／输出目标进度、曲目标识、账号、歌词、媒体地址或网页自定义字符串。

收到 `submitted` 后提前请求下一次**真实状态读取**，保留单待执行回调及超时不释放规则，不把滑条目标当成已经完成的位置；超出官方可播放／试听范围时提供明确拒绝说明，绝不绕过权益。

隔离运行保留的官方低层音频类、使用全假的音频／事件／计时器，得到 4 个反例／边界：首次播放前 seek 返回 true 但延迟到 play；已播放后暂停可 seek 而不启动播放；错误 playId 也可能返回 true；多次首次播放前 seek 会登记多个 once-play 回调，后续一次事件不等于逐请求确认。因此计数仅作诊断，不把返回 true／提交／一次 SDK 事件当作逐次实际音频跳转成功。

`lyrics3` 全量 JVM 274 项、Lint 0 error／49 warning，原签名不可调试 Release 包已验证。构建时 Redmi 一度从 ADB 断开，随后机主重新连接，于 13:59 覆盖安装并核对安装字节、UID、最新默认浏览器及原有悬浮窗权限保留。旧后台服务读取状态曾出现一次 DUMP 超时；机主允许打断前台任务后，正常打开新音乐会话，DUMP 显示 PLAYER／ready，诊断计数起始为 0。未据该次超时推断网络问题、死锁或声称新诊断解决了故障；也没有由助手开始播放。仍需机主正常播放时检查真实 seek 失败分支。

电脑内存警告后，后续构建仍串行、Gradle1536MiB／测试512MiB，并在每批前核对至少3GiB可用；没有杀其他应用或调整 swap／OOM 策略。

- 16:10旧会话读取到收到／提交各1、SDK成功2；对应真实元素是 paused=true、seeking=true、readyState=1、networkState=2、errorCode=0、最后播放 Promise 已 resolved。这说明当时元素仍在等待数据，不能据SDK回执断言已恢复播放；该较晚 seek 的发起来源尚不能从计数确定。

继续隔离运行保留的**真实官方 Howler 核心**，仅HTML媒体元素和计时器使用假对象，得到可重复分支：已播放资源 seek 到模拟未缓冲位置，会先暂停实际元素，发出 seek 回执，却等待 `canplaythrough`，此时尚未再次调用原生 play，Howler处于 loading／playLock。缓冲内的对照 seek 正常恢复；等待期间显式 pause 会排队，随后数据到达仍先尝试 play，可能被已撤销的播放授权拒绝并变成 playerror。因此官方泛化加载错误也可能来自这条取消竞争，不能直接当作网络失败。此处仍是**真实库＋假媒体的契约复现**，未证明手机根因，也没有据此伪造事件、进度或绕过官方引擎。

机主随后主动处理电脑swap／zram，助手未修改这些策略。机主另明确授权每300秒唤醒手机：仓库外临时脚本仅发WAKEUP键、与测试UI锁互斥、10秒检测断连并退出，不解锁或写系统设置。实测该键不能防止自动锁屏，故不能宣称持续亮屏；锁屏时停止交互验证，等待机主解锁。此授权不包含绕过锁屏或改变音量。

## lyrics7：当前手机系统媒体 seek 分支已修正并实测（未发布）

17:48在真正的系统媒体卡片、同一资源上重现：原生已收到／提交 seek，但在拖动**之前**恢复16秒的位置就已卡住。SDK仍报播放，实际元素却 paused／seeking、readyState=1；最后原生 play Promise 已成功，没有媒体错误。随后网络状态甚至为 idle，不据此归咎于弱网。仅将预加载设为auto的 `lyrics5` 尝试未解决，已从最终源码撤回。

修正只作用于官方原来使用、已经实际获准播放的**同一HTML音频元素**。在当前账号／文档／资源／playId仍匹配、页面仍有播放意图和原有播放授权时，若官方 seek 已将它内部暂停等待数据，则一次性继续原来的 `HTMLMediaElement.play()`，让数据和官方 `canplaythrough` 链恢复；时间目标、权益／试听坐标、媒体地址和SDK事件仍由官方控制。没有更换播放器、读取／搬运src、直接设置currentTime或伪造seek／playprogress事件，也没有因为seek而放宽WebView手势门槛。

每次真实seek回执至多一次继续；暂停清除继续标记并暂停同一元素，资源／文档变化取消旧标记。`lyrics6` 已打通播放中seek，但暂停后seek再恢复仍会等待；`lyrics7` 再只对**新的明确继续播放请求**允许同元素恢复，暂停seek本身绝不启动播放。假测试覆盖冷启动拒绝、暂停seek不播放、一次尝试不随轮询洪泛、错误资源／playId拒绝及明确恢复路径。

当前Redmi／Android16／同一资源的有限实测：

- lyrics6：冷恢复16秒不再卡住；真正后台系统滑条约17→74秒后持续增长至约79秒，元素readyState恢复4且真实时间前进。
- lyrics7：冷恢复当前官方Profile保存的79秒后正常播放；后台系统卡片向后约86→49秒、再向前约52→109秒均收到实际seek并恢复持续增长。第一段仅移动9px，未超过触摸阈值、收到计数不变，因此**不算一次seek**。
- 暂停后通过只操作本应用的MediaController辅助程序精确seek到16秒，保持暂停；再点真正系统媒体卡片的继续播放，16→18秒实际推进。随后补测原网页明确播放、Home后台、再用系统滑条约17→91秒，也恢复推进；没有将网页进度条测试冒充系统控件。
